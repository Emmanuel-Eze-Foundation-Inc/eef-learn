## Problem Statement

The Emmanuel Eze Foundation (emmanuelezefoundation.org) currently runs free 12-week bootcamps for children and teens. The foundation is pivoting to serve anyone: a place to learn any subject, connect with others on a subject matter, have 30-minute coffee chats with mentors, broadcast a need for help and get matched with people ready to help, and find physical/virtual events and training series.

The learning problem it attacks: self-learners today assemble their own curriculum from scattered YouTube videos, blogs, and courses with no map of what to learn, in what order, and no human support when stuck. MOOC research consistently shows sub-10% completion, with the top fixable causes being missing social support/presence, poor feedback, unclear prerequisites, and one-size-fits-all pacing.

## Demand Evidence

- EEF has existing program demand (free bootcamps valued at $2,500, ages 8-19) and wants to widen the funnel to all ages.
- The category is validated: multiple open-source AI learning-map generators exist (adaptive-knowledge-graph, NeuraLearn, MapScribe.ai, SkillMap, Enterprise DNA's generator), and mentor coffee-chat apps are launching commercially (Caffriend, Netup, Coffeechat).
- Gap (the eureka): no existing product combines community-composable learning maps with attribution AND human connection (mentors, help broadcasts, events). Dropout research names social support as a core cause — the map tools ignore it, the networking apps don't teach.
- Honest gap in evidence: no interviews with target learners yet. See The Assignment.

## Status Quo

A motivated self-learner googles "how to learn X", gets a roadmap blog post or roadmap.sh, opens 30 tabs, watches YouTube at random, loses the thread in week 2, and has nobody to ask. Communities (Discord, Reddit) are disconnected from the learning material. Mentorship is cold-DM LinkedIn outreach.

## Target User & Narrowest Wedge

**Target user:** an adult self-learner (EEF's widened audience) who wants to master a specific skill and wants both a structured path and humans to talk to.

### Release definition (single source of truth)

- **v1 (this plan's build target):** responsive web app. Type a topic (or upload a PDF) → AI builds a personal learning map (knowledge graph) from YouTube videos, blog links, and AI-generated content with credit to every source → travel the map in true 3D → scroll into sections whose content generates in realtime → progress saved → an always-present learning-support companion (RAG over the user's map + progress + EEF org knowledge) answers questions. The Expo mobile app is scaffolded in the monorepo from day one (shared packages compile for it) but is NOT store-released in v1.
- **v1.5:** Expo iOS/Android store releases (EAS), after the web wedge is validated with real learners. (Reviewer recommended post-validation store release; user's requirement that the platform be mobile-deployable is preserved by the day-one scaffold. Flagged for user confirmation at the autoplan gate.)
- **v2 (community):** publish maps for others to find/use, compose maps from other maps with attribution and permissioned update propagation, Mentor Match (swipe UI, 30-min coffee chats), help broadcasts, events listings.

The v1 wedge is accurately a **personal map generator**; the community mechanics that make it a "community knowledge generator" land in v2. Why the social differentiator can wait one release: the composition/attribution schema is designed into the v1 data model (so no migration cliff), while the companion bot supplies v1's support presence. Shipping generation first produces the maps that mentors and the community then attach to.

## Constraints

- Open source on GitHub under an EEF org; must be self-hostable (docker-compose) alongside the hosted flagship.
- Web-first mobile-responsive; iOS/Android apps from shared codebase (store release at v1.5, see Release definition).
- True 3D map navigation is the primary v1 experience (user decision, D4, amended): 3D renders on all devices meeting the performance budget (200 nodes at 30fps on a mid-tier 2022 Android / any desktop); devices below budget automatically fall back to the 2D map view. The 3D spike's pass/fail covers BOTH the node-count budget AND the riskiest interaction: scroll-driven camera flight synchronized with a DOM content column overlaying the canvas (section view) at 30fps — the hybrid canvas/DOM scroll sync, not just raw rendering. Spike decision deadline is before the map UI milestone starts. If the spike fails globally (budget unreachable even on desktop), that reverses decision D4 and goes back to the user: the prepared fallback is 2D map primary with 3D as progressive enhancement — never silently adopted.
- Creator-only regeneration; admins can enable/disable per-user path generation/regeneration. "Admin" = EEF staff role on the hosted instance; the instance operator on self-hosted deployments. Settings are per-user and per-map.
- Attribution is mandatory: external sources (YouTube, blogs) and upstream community maps must be credited.
- Blog sources in v1 are **link + oEmbed/OpenGraph metadata only** (title, author, thumbnail) — no excerpt scraping, avoiding copyright and extraction complexity. Full-text ingestion only for user-uploaded PDFs they have rights to.
- Composed maps: upstream changes require learner permission to apply — accept all or per-component.
- PDF import: user chooses "stick to the doc" or "doc + AI additions".
- Nonprofit budget: prefer generous free tiers and low-ops services.
- **Cost controls (hosted):** per-user daily quotas (default: 3 new maps, 30 section generations, **100 companion-bot messages**/day, admin-tunable), per-request token ceilings, and a global daily spend cap that flips generation to a queued "come back later" state (bot degrades to retrieval-only answers). Estimated cost per full map generation: $0.10–$0.50 depending on provider (skeleton ~2k output tokens + per-section 1-3k) — must be re-measured at implementation.
- **Age policy:** v1 hosted instance is 13+ (Better Auth birthdate gate at signup); under-18 accounts get minor-safe companion-bot system prompts and are excluded from future mentor matching until the v2 trust/safety design lands. Legal review of COPPA/GDPR-K posture is a Dependency.

## Approaches Considered

### Approach A: Minimal viable (rejected during session)
Single Next.js app, 2D map, no mobile scaffold. Rejected: contradicts the true-3D v1 requirement and would strand mobile (v1.5) without shared packages, forcing a rewrite.

### Approach B: Ideal architecture — TypeScript monorepo + Python AI service (CHOSEN)
Turborepo monorepo: Next.js web + Expo mobile sharing core packages, FastAPI Python AI service, Postgres as the single stateful store.

### Approach C: Fork an existing OSS generator (rejected during session)
Head start on generation, but foreign architecture fights composable maps, 3D, attribution semantics, and mentor matching.

### Core domain model (v1)

- `Map` (learning map): owner, title, visibility (private/published), **version (integer, incremented on every regeneration or structural edit; composition pins to a version)**, generation settings (enabled/disabled per user by admin), source policy (stick-to-doc / augment)
- `Node` (concept/section) + `Edge` (prerequisite): the knowledge graph. **Node identity is a stable slug derived from the concept name, preserved across regenerations**: regeneration produces an old→new node mapping; progress on unmapped (deleted) nodes is archived, not lost, and surfaced to the learner as "this section changed."
- `Section content blocks`: typed — `youtube` (URL + credit), `blog` (link + oEmbed/OG metadata + credit, no scraped excerpts), `ai_text` (generated realtime; provenance recorded: model id, prompt hash, retrieved source block ids), `pdf_extract`
- `Attribution`: every block and every composed sub-map carries source credit
- `MapComposition` (schema in v1, UI in v2): parent map ↔ component map refs pinned to a `Map.version`; upstream version bumps create `UpdateProposal`s learners accept all-or-individually
- `Progress`: per user per node/section, powers the support bot's awareness
- `CompanionThread`: learning-support bot conversations. RAG = pgvector semantic search + Postgres full-text search (hybrid, reciprocal rank fusion) over map content, the user's progress, and the EEF org knowledge base. **Org KB corpus (v1):** markdown files under `docs/kb/` in the repo (mission, programs, FAQ — seeded from emmanuelezefoundation.org content) plus admin-editable KB pages stored in Postgres; both are chunked and embedded on change by the AI service. Bot "skills" = a fixed v1 tool list: mark section complete, jump to node, explain current section differently, regenerate section (creator only, if enabled), cite sources for a claim.
- v2: `MentorProfile`, `MatchSwipe`, `CoffeeChat`, `HelpBroadcast`, `Event`

### Web ↔ AI service integration contract

- Hosting: the FastAPI service is a long-running process and cannot run on Vercel — hosted flagship deploys it to **Railway** (or Fly.io; both have low-cost hobby tiers), reachable over TLS. Self-hosters get it as a container in docker-compose.
- Transport: HTTP over TLS. The Next.js server calls FastAPI over REST to enqueue work. The browser never calls the AI service directly.
- Streaming without a relay: the AI service writes progress checkpoints and content blocks to Postgres (`GenerationJob` rows: `queued → running → done/failed` + checkpoint payloads, with lease/heartbeat claiming and idempotent resume). The browser polls a checkpoint endpoint with a last-seen-id resume token (**polling is the primary transport** — amended 2026-09-13 per eng review: LISTEN/NOTIFY requires dedicated long-lived connections that Neon's pooler doesn't support and Vercel functions can't affordably hold, so it would pass locally and fail only in production; it remains available as a self-host-only latency optimization with signal-only payloads). Postgres is the single coordination point, and long jobs survive web restarts.
- Interactive chat (companion bot) is latency-sensitive and runs on the TS side via the Vercel AI SDK directly against the model provider, using the AI service's single `/retrieve` endpoint (query embedding + hybrid search + RRF owned in one place; the TS side never embeds — amended 2026-09-13 per eng review). The Python service owns batch/pipeline work: map generation, section generation, enrichment, embedding ingestion.
- Auth between services: shared bearer service token (env `AI_SERVICE_TOKEN`), rotated by the operator; TLS in transit (no private-network assumption).
- Degraded modes (user-visible behavior): YouTube quota exhausted → map generates with AI-text + blog links only, video slots marked "video suggestions unavailable, retry later"; AI provider error mid-stream → section shows retry affordance, partial content persisted; PDF parse failure → explicit error with "try text paste instead"; global spend cap hit → generation queued with position shown.

### Sourcing & quota strategy (YouTube)

Default YouTube Data API quota is 10,000 units/day (~100 searches). Mitigations designed in from day one: (1) search results cached in Postgres keyed by normalized query — cache hit costs zero quota; (2) map skeleton generates WITHOUT YouTube (AI + structure first), video enrichment runs as a separate lower-priority job; (3) quota-increase application filed as a launch Dependency; (4) self-hosters bring their own key.

### The 3D map experience (core UX flow)

1. **Map view:** the knowledge graph renders as a 3D constellation (force-directed layout, prerequisite edges as paths). Camera orbits/zooms freely; nodes show mastery state by color/glow.
2. **Enter a node:** clicking (or scrolling toward) a node flies the camera along the path into that node — the "travel" moment. The node expands into its section view.
3. **Section view:** a scrollable content column (the node's typed blocks in order) with the mini-map staying pinned beside it (the "map on the side"). Scrolling past the last generated block triggers realtime generation of the next block (skeleton-first: headings render instantly, content streams in).
4. **Controls:** per-section regenerate button (visible only to the creator, only when regeneration is enabled), source credits footer per block, "ask the companion" affordance anchored to the current section.
5. **Exit/continue:** scrolling past the section end flies the camera to the next recommended node; progress checkpoint saves on every block completion.

### Retention design (from MOOC research)

- Visible progress on the 3D map (mastery states per node)
- Short early wins: first section generates in seconds, no long assessments up front
- Social presence from day one of v1.x: companion bot in v1, humans (mentors/help broadcasts) immediately after
- Clear prerequisites encoded in the graph itself

## Success Criteria

- **p90 under 60 seconds from topic submit to first rendered section block** (skeleton-first streaming: graph skeleton streams before enrichment; video enrichment async). Instrumented via generation-latency and failure-rate metrics on `GenerationJob` (this is the v1 observability minimum, alongside AI spend per day).
- Progress persists across sessions and devices; companion bot correctly references the user's current node.
- Every external source visibly credited; the composition schema records upstream lineage (UI in v2).
- Repo is publicly cloneable and boots with `docker compose up` + one seed command.
- v1 ships responsive web with true 3D on budget-meeting devices; the Expo app compiles and runs in development against the same API (store release = v1.5).
